# 契约 02 · 扩展点（serde 同构）

> **作者**：Mimo-V2.6-Pro · 2026-09-23 · 状态：**定稿**  
> **crate**：`jev-core`（trait + registry）· 适配器在 `jev-adapters` 或**外部 crate**  
> **对齐**：Q1=A 编译期 trait 同构；为可拓展性做准备。

## 1. serde 同构性（合同条款）

| serde | 本契约 |
|---|---|
| 给类型 `impl Serialize` | 给厂商 `impl ProtocolAdapter + UpstreamAdapter` |
| 内核 `to_string(&x)` 不关心 x | 内核 `invoke(&req)` 不关心对面是谁 |
| 加类型不改 serde 源码 | **加提供商不改 jev-core / jev-protocol / daemon 一行** |
| 调用点传参不变 | `invoke` / `register` 签名**永久冻结** |

**「能用」的定义（Q1 追问已答）**：别的 crate 能依赖它并被编进 bin 使用。**不是**「daemon 不重启热插拔」（那是 B，本期不做）。

## 2. 冻结 API

```rust
// jev-core —— 签名冻结。变更 = 破坏性版本 + 迁移说明。
pub trait ProtocolAdapter: Send + Sync {
    /// 出站方言化。默认恒等。
    fn outgoing(&self, req: JevRequest) -> JevRequest { req }
    /// 入站归一化：厂商原始 bytes → 标准 JevResponse。
    fn incoming(&self, raw: &[u8], ctx: &IncomingCtx<'_>) -> Result<JevResponse, JevError>;
    /// 本适配器的方言 id（vercel_boolean / typesafe / …）
    fn dialect(&self) -> &'static str;
}

pub struct IncomingCtx<'a> {
    pub request: &'a JevRequest,       // outgoing 之后的请求（用于按 qid 还原语义）
    pub original: &'a JevRequest,      // 调用方原始请求
    pub status: u16,
}

#[async_trait]
pub trait UpstreamAdapter: Send + Sync {
    fn id(&self) -> &str;
    fn capabilities(&self) -> Capabilities;
    async fn evaluate(&self, req: JevRequest) -> Result<JevResponse, JevError>;
}

pub struct Registry { /* … */ }
impl Registry {
    /// 传参永不因新厂商而改。
    pub fn register(&mut self, up: Box<dyn UpstreamAdapter>);
    pub fn invoke(&self, req: JevRequest, ctx: RouteCtx) -> Result<JevResponse, JevError>;
}
```

## 3. 分层铁律

| 层 | 允许出现 | 禁止出现 |
|---|---|---|
| `jev-protocol` | 内核类型、`noul_probability` | 厂商字段名、URL、header |
| `jev-core` | trait、Router、RetryPolicy、Capabilities | `match "vercel"`、具体 URL |
| adapter crate | 厂商 DTO（自 derive）、HTTP、方言翻译 | 修改 core 签名、往 `JevResponse` 塞专有字段（只进 `extra`） |
| daemon | axum、config 加载、registry 装配 | 业务选路/翻译逻辑 |

## 4. 黄金测试（通过才能加新厂商）

在 **SysTorch 仓库之外** 的 crate `my_lab_adapter`：

1. 自定义怪异 DTO：`{"verdict":"yes","odds":0.8}`
2. `impl ProtocolAdapter` + `impl UpstreamAdapter`
3. **零修改** `jev-core` / `jev-protocol` / daemon
4. `registry.register(...)` 后 `POST /v1/systemone` 换 `model` 命中
5. 响应已是标准 `JevResponse`（`Noul { noul|probability }` 等）

**红线（打回条件）**  
加提供商若需要：改 core 的 `match`、改 `invoke`/`register` 参数、往 `JevResponse` 正式字段加厂商键 → **设计失败**。

## 7. SysTorch 请求扩展的语义保持规则（2026-10-29）

新增适配器仍遵守契约 01 的持久异步与媒体兼容补充：

1. 适配器可以把 TypeSafe-compatible `model/state/questions` 请求转换为上游传输方言，但必须保留每个 question ID、类型、instructions、criteria、state 与资产引用的含义；响应还原时 answer ID 必须一一对应。
2. 添加 `task_id`、`status`、`revision`、`deadline`、幂等键或媒体传输信息只能扩展既有请求/响应，不得用另一种异步专用 schema 取代 Jev 问题合同。
3. 图片/音视频/文件等能力须由目标具体模型/端点声明或经实测确认；UI 选择附件时不得根据当前 Provider 预先过滤，资产必须随 SysTorch 请求保留。适配器不得为了让请求“看起来成功”而删除扩展字段或媒体；无法保持语义时，在网络调用前以稳定 `format_mismatch` / capability mismatch 提示，并保留原请求/附件供重新选择兼容入口。
4. 新适配器的黄金测试应加入多题映射、异步加法字段、资产 ID 与引用往返，以及不支持题型/媒体的 fail-fast 用例。现有单题 Choice 实现不得作为多题或多模态兼容性的证明。
5. SysTorch 的资产登记表按通用 modality 扩展，至少保留图片、音频、视频/帧及通用文件/未知 MIME；图片是当前已核实的 TypeSafe 映射，其他类型可复用稳定 ID、内容句柄与 question/state 引用，但不得据此假定某个上游已支持。将来若需要转码、转写或抽帧，应由显式的兼容适配节点处理并在路由/调用详情中可追溯，不允许 adapter 私下做有损转换。
6. SysTorch API 是规范超集；TypeSafe API 是仅针对其支持子集的投影。Provider adapter 可将小媒体的 base64 或大媒体的 SysTorch asset ID 转成上游的 JSON/base64 或 multipart 表达，但仅当语义与引用位置不变。若剔除 SysTorch 扩展字段会丢失请求所需的媒体/任务含义，该请求不得走 TypeSafe 投影。

本规则约束协议与 adapter 行为；不要求为每种模型增加 SysTorch 专用环境变量，也不提前引入动态插件、全局事件总线或通用 schema 执行引擎。
